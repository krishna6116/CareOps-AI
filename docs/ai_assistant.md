# CareOps assistant

`POST /assistant/ask` answers questions about the latest run. The answer is
computed from saved outputs, not generated by a language model.

## How an answer is produced

1. **Route.** `backend/app/services/assistant_facts.py` maps the question to
   an intent with keyword rules: bed availability N days out, department
   capacity pressure, unassigned bed requests, baseline vs optimized
   allocation, staff coverage, model reliability, model limitations,
   recommendations, ICU / admission / occupancy forecasts, or a what-if
   scenario. Anything else gets an overview and a list of supported
   questions.
2. **Compute.** The intent reads the saved files it needs. For example, it
   sums `forecast_available_beds` across departments for the cutoff date + N
   days, or reads reason counts from `bed_assignment_summary.json`. It
   returns:
   - `answer`
   - `evidence`: each item has a label, value, kind and source file. The kind
     is `observed` (synthetic history or inventory), `forecast`,
     `model_metric` or `simulated`.
   - `sources`
   - `limitations`
   - `evidence_run_id`

   Counts are whole numbers. Model metrics keep their decimals.
3. **Scenarios.** "What happens if admissions increase by 20%?", "ICU beds
   decrease by 3" or "staff availability decreases by 10%" first run the
   OR-Tools what-if simulation (`simulation_ran: true`). The answer then
   explains that saved run. It states that forecasts were scaled, not
   retrained.
4. **Optional rephrasing.** With `CAREOPS_LLM_PROVIDER=openai` (needs
   `OPENAI_API_KEY`) or `ollama` (loopback URL only), the provider receives
   the question, the grounded answer and allowlisted aggregate context. It is
   told only to rephrase. Patient-level rows are never sent. A number in its
   output that does not appear in the grounded answer, the context or the
   question causes a rejection.
5. **Fallback.** If the provider is not configured, unavailable, times out,
   rejects credentials, returns malformed output or fails the number check,
   the API returns the grounded answer with `assistant_provider:
   "deterministic"` and a `fallback_reason`. The audit record is stored with
   status `fallback`. Nothing falls back silently.

The default provider is `deterministic`, so the assistant works without an
API key.

## Response fields

`answer`, `intent`, `evidence`, `limitations`, `sources`, `source_run_id`,
`evidence_run_id`, `simulation_ran`, `assistant_provider` (the explainer
actually used), `llm_configured` and `fallback_reason`.

## Audit

`GET /audit/assistant` returns recent requests. Each entry holds the question
(with anything that looks like an API key redacted), the configured provider
and model, the status (`success`, `fallback` or `error`), sources, latency,
run ID and error text. API keys and authorization headers are never stored or
returned.

## Boundaries

- The services do the calculations. The assistant never creates forecasts,
  metrics or recommendations.
- It distinguishes the ICU admissions forecast from ICU census.
- It does not make clinical decisions or execute operational actions.
- All data is synthetic. The API has no user authentication, so do not expose
  it publicly or enter real patient information.

Tests: `backend/app/tests/test_api.py` checks every example question from the
project brief against the saved outputs. It also covers the OpenAI and Ollama
fallbacks and the rejection of unverified numbers.
