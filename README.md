# CareOps AI — Hospital Operations Forecasting and Resource Planning

[![CareOps-AI CI](https://github.com/krishna6116/CareOps-AI/actions/workflows/ci.yml/badge.svg?branch=master)](https://github.com/krishna6116/CareOps-AI/actions/workflows/ci.yml)

A decision-support portfolio project. It forecasts hospital admissions, occupied
beds, ICU admissions, length of stay and appointment no-shows, then uses Google
OR-Tools to plan beds, staff shifts and appointments against those forecasts.
A FastAPI service and a React dashboard present the results.

**Live demo: [krishna6116.github.io/CareOps-AI](https://krishna6116.github.io/CareOps-AI/)**. This is a
static snapshot of the dashboard exported from the real API for the 2026-10-05 run. The assistant
and simulator show precomputed results for the example questions and presets. Run the project
locally (below) for the live API.

> **Synthetic data only.** Every patient, bed, shift and appointment is
> generated. Nothing here has been validated on a real hospital, and the
> outputs are not clinical or staffing decisions. See
> [Limitations](#limitations-and-synthetic-data).

## The problem

Bed managers and staffing coordinators plan days to weeks ahead with uncertain
demand. Too little capacity means boarding and cancelled procedures; too much
wastes staff hours. This project asks two questions:

1. **How well can we forecast demand 30 days ahead**, and does a machine-learning
   model actually beat simple rules of thumb?
2. **Given those forecasts, what bed, staff and appointment plan satisfies the
   operational constraints**, and what extra capacity would a feasible plan need?

## Architecture

```mermaid
flowchart LR
  G[Synthetic data generator<br/>data/synthetic] --> V{Source integrity checks}
  V --> A[Admissions forecast<br/>XGBoost vs naive baselines]
  V --> L[Length-of-stay model]
  V --> O[Occupancy forecast<br/>Ridge vs naive baselines]
  V --> I[ICU admissions forecast]
  V --> N[No-show model]
  A & L & O & I --> B[Bed availability projection<br/>whole beds]
  B --> R[OR-Tools CP-SAT<br/>beds, staff, appointments]
  N --> R
  V --> Q[Request-level bed replay<br/>baseline vs CP-SAT]
  R & Q --> S[Reliability scorecard<br/>+ run manifest]
  S --> M[docs/MODEL_METRICS.md]
  S --> API[FastAPI] --> UI[React dashboard]
  API --> AS[Grounded assistant<br/>evidence + sources]
  API <--> PG[(PostgreSQL<br/>simulations, audit,<br/>pipeline handoff)]
  V -.--exploratory.-> E[Cleaning, EDA,<br/>feature tables]
```

Each forecast is published only after a 30-day rolling-origin backtest against
naive baselines. If the learned model does not win, the baseline forecast is
published.

### Planning results (simulation, not model accuracy)

**30-day department plan.** The optimizer finds a plan with zero bed, ICU and
emergency overflow and no unfilled shifts. It needs **scenario-only** extra
capacity to do so: temporary surge beds and a synthetic flex-staff pool, both
listed in `optimization/resource_planning/outputs/capacity_expansion_plan.csv`.
Its baseline and optimized bed KPIs are identical, because projected demand
(about 60% of beds) fits capacity and pooling has nothing to improve.

**Request-level bed allocation.** `optimization/bed_assignment.py` replays the
actual synthetic arrivals of the 28 days to 2026-10-05 against the census
rebuilt for each day, using the same rules for both policies:

| Policy | Requests | Assigned | Off-service | Compatibility violations |
|---|---:|---:|---:|---:|
| Baseline: arrival-order first fit, home ward only | 315 | 288 | 0 | 0 |
| CP-SAT: severity-weighted, off-service penalty | 315 | 311 | 22 | 0 |

All 28 daily models solve to OPTIMAL. Every unassigned request has a reason code.
This replaces an earlier study whose 146 "requests" were 31–61 days old
admissions placed on a single day; see
[docs/BED_ALLOCATION_DIAGNOSIS.md](docs/BED_ALLOCATION_DIAGNOSIS.md).

**Staff scheduling.** Both policies use the same 30-day requirements, availability, rest and
hour rules (`staff_schedule_comparison.csv`):

| Policy | Unfilled positions | Surge shifts | Overtime shifts (hours) | Workload spread (std, h) | Shift-preference match |
|---|---:|---:|---:|---:|---:|
| First fit, base staff first, no overtime | 27 | 2,512 | 0 (0) | 44.1 | 52.5% |
| CP-SAT with costed overtime | 0 | 2,365 | 424 (1,500) | 31.0 | 92.2% |

A full overtime shift is costed above a surge shift, so overtime is mostly partial. An earlier
weighting put base staff on overtime most weeks (2,211 shifts) to save surge staff and was
rejected.

**Appointments.** The last 7 clinic days: 838 of 838 appointments booked, doctor double-bookings
77 → 0, bookings with off-shift doctors 254 → 0. No-show risk never changes bookings. It flags
217 appointments for reminder outreach at the model's validation threshold (0.18) and estimates
4,287 expected idle minutes for overbooking review.

These results show that plans are feasible and that rules are respected under
the model's assumptions. They are not measured improvements, and this project
makes no claim about real-world savings or outcomes.

## How to run

Requirements: Python 3.14 (pinned in `.python-version`; CI and Docker use the
same version) and Node 24 for the dashboard (Vite 8 and Vitest 5).

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt

# Full pipeline: data → forecasts → optimization → scorecard → docs/MODEL_METRICS.md
# The cutoff defaults to the last date in data/synthetic (2026-10-05).
.\.venv\Scripts\python.exe run_portfolio.py

# Also rebuild the cleaned data, EDA reports and exploratory feature tables
.\.venv\Scripts\python.exe run_portfolio.py --exploratory

# Quick smoke run on a small scenario (what CI runs); do not commit its outputs
$env:CAREOPS_SCENARIO_SCALE = "0.25"
.\.venv\Scripts\python.exe run_portfolio.py --as-of-date 2025-06-30
Remove-Item Env:\CAREOPS_SCENARIO_SCALE

# Tests (data, models, optimization, API); run from the project root
.\.venv\Scripts\python.exe -m pytest -q
```

Generators and models use fixed seeds. The same date, code and dependency
versions reproduce the same data and forecasts. `requirements-lock.txt` records
the exact package versions behind the committed outputs. A run exits nonzero and lists
its blockers in `portfolio_run_manifest.json` if any reliability section is
below 4/5 or a capacity gate fails. Passing a new `--as-of-date` regenerates
the synthetic data up to that date; the committed outputs are for 2026-10-05.

### API and dashboard

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
# API docs: http://localhost:8000/docs

Set-Location frontend
npm ci
$env:VITE_API_URL = "http://localhost:8000"
npm run dev   # http://localhost:5173
```

The API serves the saved pipeline outputs. Alerts, what-if simulations and the
assistant audit are stored in the database: SQLite by default, PostgreSQL when
`CAREOPS_DATABASE_URL` is set. `/health` reports the database, `/ready` returns
503 until a database and a completed run are available, and `/meta` describes
the run.

Dashboard checks, from `frontend/`: `npm run typecheck`, `npm test` (Vitest),
`npm run build`, and `npx playwright test` (browser tests of every page against
the live API; see [docs/frontend.md](docs/frontend.md)). `npm run build:demo`
builds the static GitHub Pages demo from a snapshot exported by
`deploy/export_demo_snapshot.py`.

### AI assistant

The assistant answers from calculated results, not from a language model. Each
question is routed to an intent, such as bed availability in N days,
department pressure, unassigned requests, baseline vs optimized,
staff coverage, forecast reliability, limitations, recommendations or what-if
runs. The answer is computed from the saved outputs and returned with
evidence. Each evidence item is labelled observed, forecast, model metric or
simulated, with source files and the run ID.

No API key is needed. With `CAREOPS_LLM_PROVIDER=openai` (and
`OPENAI_API_KEY`) or `ollama` (loopback URL only), the model only rephrases
the grounded answer. Any number in its output that does not appear in the
evidence is rejected. If the provider is missing, fails or is rejected, the
grounded answer is returned with a `fallback_reason`, and the audit log
records it. The assistant does not make clinical decisions or take actions.
See [docs/ai_assistant.md](docs/ai_assistant.md).

### PostgreSQL

```powershell
$env:CAREOPS_DATABASE_URL = "postgresql+psycopg://USER:PASSWORD@HOST:5432/DATABASE"
.\.venv\Scripts\python.exe -m alembic -c backend/alembic.ini upgrade head   # application tables
.\.venv\Scripts\python.exe run_portfolio.py --as-of-date 2026-10-05 --postgres  # optional handoff
```

`--postgres` loads source data, forecasts and optimization outputs into a
`careops` schema in one transaction, tagged by `run_id`; reloading a run
replaces it. To run the PostgreSQL tests, point `CAREOPS_TEST_DATABASE_URL`
at a disposable database:

```powershell
$env:CAREOPS_TEST_DATABASE_URL = "postgresql+psycopg://USER:PASSWORD@localhost:5432/careops_test"
.\.venv\Scripts\python.exe -m pytest backend/app/tests/test_postgres_integration.py -v
```

The psycopg driver is already in `requirements-lock.txt`. Common setup problems
are covered in [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md).

## Forecasting rules

- **Time-based splits only.** No shuffling. Lags and rolling features use data
  up to the previous day.
- **Naive baselines everywhere:** last value, same weekday last week, 7- and
  28-day moving averages. Metrics: MAE, RMSE, sMAPE, MASE and bias.
- **Whole numbers at the output layer.** Admissions, beds and ICU admissions are
  published as non-negative integers, and occupied beds are capped at bed
  capacity (`ml/count_outputs.py`, covered by unit tests). Department
  admissions are reconciled so they add up to the hospital total. Evaluation
  files keep raw model output for scoring.
- **Prediction intervals** are split-conformal, use the backtest errors, and are
  reported with their measured coverage.

## Limitations and synthetic data

- **Synthetic data.** The generator encodes its own assumptions about arrival
  rates, seasonality, length of stay and no-show behaviour. Models that do well
  here are learning the generator, not a hospital. Real data would bring
  missing values, coding changes, reporting delays and shocks that are absent here.
- **Simulation warm-up.** The simulated hospital opens empty on 2024-01-01:
  discharges are near zero in the first week and occupancy overshoots while the
  first patients are in hospital. The first 21 days are excluded from training,
  validation and evaluation for every model (`ml/scenario_config.py`; a test
  checks the cutoff against the generated data). History features may still
  look back into those days.
- **Retrospective evaluation only.** Time-series backtests use 24 weekly
  origins on one simulated history. That is not a prospective trial, and
  interval coverage measured on the later origins is noisy.
- **Admissions are near noise.** The published admissions forecast is a 28-day
  moving average because nothing tested beat it.
- **ICU scope.** The ICU model forecasts admissions, not ICU census. Census is
  projected in planning from admissions and predicted LOS.
- **Staffing data.** The synthetic shift roster was generated independently of
  the ward census. The allocation replay therefore reports rostered-staffing
  exceedances rather than enforcing them. Enforcing them places only 55 of 315
  requests, which reflects the data artifact rather than a finding.
- **Scenario scope.** What-if runs scale the saved forecasts and rerun the
  department allocator and emergency model. They do not retrain forecasts or
  rerun the request-level replay.
- **Planning feasibility depends on scenario capacity.** Zero overflow is
  achieved with synthetic surge beds and flex staff. Costs are illustrative
  assumptions, not quotes.
- **Whole-number rounding.** Published bed-projection columns are rounded one
  by one, so `current + admissions − discharges` may differ from the projected
  beds by a unit.
- **Not for clinical use.** The no-show score must not be used to deny or
  deprioritise care. All outputs are intended for review by qualified staff.
